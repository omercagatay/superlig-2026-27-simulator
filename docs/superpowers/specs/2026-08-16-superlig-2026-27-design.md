# Trendyol Süper Lig 2026-27 Simulator — Design

Date: 2026-08-16
Status: approved design, pending implementation plan

## Goal

Transform the 2026 FIFA World Cup Monte Carlo simulator into a Monte Carlo
simulator for the 2026-27 Trendyol Süper Lig season.

This is an **in-place transformation**, not an abstraction over both formats.
The World Cup finished; there is no second competition to serve. The
tournament machinery is deleted rather than generalized.

### Kept (format-agnostic)

- `World` + the deterministic seeded `rayon` trial loop
- The three-model strength ensemble (Elo / Dixon-Coles / pi-ratings) and its
  `ENSEMBLE_WEIGHTS` blending
- `handlers.rs` route shapes, per-IP rate limiting, `AppState`
- The LLM scenario flow: prompt → JSON adjustments → server-side validation →
  simulate on a cloned `World`
- The Wikipedia scrape-and-overlay pattern
- Static-file serving of the built SPA

### Deleted

Groups, third-place qualification (`assign_thirds`, `third_place_slots`,
`actual_third_assignment`), the knockout bracket graph (`r32`/`r16`/`qf`/`sf`/
`FINAL`), `ko_match`, `ko_winner`, extra time (`ET_FACTOR`), penalty shootouts
(`PEN_DAMP`), `played_knockout`, `knockout_out`, the representative-bracket
picker, `BracketView.tsx`, `GroupTables.tsx`, and the eloratings.net scrape.

## 1. Competition structure

Verified against the 2026-27 Süper Lig Wikipedia page on 2026-08-16:

- **18 clubs**, double round-robin, **34 matchdays**, **306 fixtures**
- **Relegation:** bottom 3 to TFF 1. Lig
- **Europe:** 1st-2nd → Champions League, 3rd → Europa League, 4th →
  Conference League
- **Season start:** 14 August 2026 (already under way; the design must
  tolerate a partially-played season from the first deploy, never assume
  zero matches played)

### Ranking rules — verified, and different from the World Cup's

Quoted from the season page:

> Rules for classification: 1) Points; 2) Head-to-head points; 3) Head-to-head
> goal difference; 4) Head-to-head goals scored; 5) Goal difference; 6) Goals
> scored; 7) Play-off.

Head-to-head is applied **before** goal difference. The World Cup code ranked
points → GD → GF, so this cannot be carried over. Relegation probabilities are
sensitive to the difference.

### Fixtures

`fixtures() -> Vec<Fixture>` returns all 306 fixtures as
`(round, home, away)`, taken from **the official TFF calendar** at
`https://www.tff.org/default.aspx?pageID=198`.

The whole season is embedded in that single page — 306 distinct `macId` links
grouped under 34 `N. Hafta` headings, in `<td>home</td><td>score</td>
<td>away</td>` rows. Extracted and structurally validated on 2026-08-16:

- 306 fixtures, 34 rounds × 9 fixtures each
- 18 clubs, exactly 34 matches each
- 153 distinct unordered pairs, each appearing exactly twice
- every *ordered* pair exactly once — home and away correctly reversed

This supersedes the earlier plan to generate rounds by the circle method: the
real calendar is available, so `/api/upcoming` reports genuine matchdays and
the "canonical schedule, not the official calendar" caveat is dropped.

The page is served as **windows-1254**, not UTF-8. Decoding it as UTF-8
mangles every Turkish club name; the fetch script must decode explicitly.

## 3. Simulation core (`src/sim.rs`)

`World` drops `host`, `groups`, `played_knockout`, `knockout_out`; gains
`fixtures`. `played` is re-keyed as above.

### Home advantage becomes structural

The World Cup applied `HOME_ADV` via a per-team `host: Vec<bool>` flag —
correct for a tournament with three host nations, wrong for a league where
every club is home half the time. `lam_pair(ia, ib)` becomes
`lam_pair(home, away)`, with the home boost applied to the fixture's home
side. Dixon-Coles `gamma` and the pi-ratings home lambda align to the same
convention. This touches every call site, including `match_win_probs` and the
ensemble's own `lam_pair`.

### Per trial (`simulate_one`)

1. Walk all 306 fixtures. Use the recorded result when present, otherwise
   sample a scoreline (Dixon-Coles joint distribution when DC carries weight,
   independent Poissons otherwise — unchanged logic).
2. Accumulate per-club points, GF, GA, W/D/L, plus the pairwise result map
   needed for head-to-head.
3. Rank via `rank_table` (§4).
4. Emit finishing positions.

### Aggregation (`SimResults`)

- `position_counts: Vec<[usize; 18]>` — the P(team, position) grid
- `title_counts`, `ucl_counts`, `uel_counts`, `uecl_counts`, `europe_counts`,
  `relegation_counts`
- `points_sum`, `gd_sum` → expected points and expected GD
- `pairwise_above: HashMap<(usize, usize), usize>` → title-race head-to-heads
- Representative final table: the trial whose per-position outcomes most often
  match the per-position mode, replacing the representative bracket

### Determinism

Unchanged: `config.seed.wrapping_add(i * 2654435761)` per trial. This is a
hard invariant with an existing test that must survive the rewrite.

## 4. `rank_table` — head-to-head ranking

The riskiest logic in the rewrite. `rank_group` already does head-to-head
sub-sorting for tied blocks; `rank_table` follows that precedent at league
scale.

1. Sort all 18 clubs by points, descending.
2. For each maximal block of clubs tied on points with `len >= 2`, build a
   mini-table from **only the matches among that block**, and re-sort the
   block by H2H points → H2H GD → H2H GF.
3. Clubs still tied after H2H fall back to overall GD → overall GF.
4. Anything still tied is resolved by a seeded coin flip, standing in for the
   real play-off. Deterministic given the trial's RNG.

**Stated assumption — H2H is applied once, not recursively.** When head-to-head
partially splits a tie (a 3-way tie where H2H separates one club and leaves two
still level), those two fall through to overall GD/GF rather than to a fresh
H2H mini-table computed among just the pair. Federations differ on this and the
quoted rule does not specify it. One pass is the reading we implement, and the
hand-built tie test in §11 asserts exactly this behavior so the choice is
pinned rather than incidental.

The "head-to-head applies only once all matches between the tied teams are
complete" caveat is moot inside a trial: every trial simulates a full season,
so all H2H matches always exist.

## 7. History and the ensemble

### Source: Wikipedia wikitext

Süper Lig season pages carry the results matrix as a `{{#invoke:sports results}}`
call in a fully machine-parseable form:

```
| name_GAL     = [[Galatasaray S.K. (football)|Galatasaray]]
| match_ADE_GAL = 1–5
```

`match_<HOME>_<AWAY> = h–a` gives home/away orientation directly; `name_<CODE>`
gives the canonical display name. **Verified reachable and parseable for all 14
seasons from 2012-13 through 2025-26** (2025-26 complete at 306 matches),
roughly 4,400 matches total.

This replaces the originally-planned football-data.co.uk `TUR.csv`, which the
network proxy blocks. Wikipedia is the better source regardless: deterministic
to parse, self-checking (below), and it shares one spelling convention with the
live scraper.

### Name drift across seasons — still the largest silent-failure risk

Using one source removes the *cross-source* alias map but not the
*cross-season* one. Display names drift between seasons of the same source:
Başakşehir appears as "İstanbul B.B." in pre-2014 seasons, Gaziantep as
"Gazişehir Gaziantep" around 2019, and "Fatih Karagümrük" versus "Karagümrük"
varies. Any season where a current club's display name fails to string-match
its canonical 2026-27 name silently dumps that club's history into the
fallback bucket — quietly weakening a real club, the same failure mode as
before in a new location.

Mitigation, in order:

1. The converter dumps the distinct team-name set across all 14 seasons.
2. A hand-built season-name → canonical-name map is checked in.
3. The build **asserts a per-club expected season count** (Galatasaray 14,
   Amedspor 0, Erzurumspor its actual top-flight seasons, and so on). This
   assertion, not the map, is the regression net: it fails loudly when a
   future rename or a new season breaks a match.

### Fetching

Wikipedia rate-limits rapid sequential requests, returning a short stub page
rather than an error. The fetch script must send a descriptive user-agent,
sleep between requests, and **assert a plausible byte count and match count per
season** so a throttled stub fails loudly instead of silently yielding an empty
season.

### Self-check

Each season page also publishes a standings table (`win_XXX`, `draw_XXX`,
`loss_XXX`, `gf_XXX`, `ga_XXX`). The converter recomputes standings from the
parsed matrix and diffs them. Two real complications found while verifying
2024-25, both of which must be handled rather than asserted away:

1. **Team codes differ between the two tables on the same page** — the results
   matrix uses `RİZ`/`SİV` (dotted İ) while the standings table uses
   `RIZ`/`SIV` (ASCII I). Codes must be normalized before matching.
2. **Withdrawals, forfeits, and points deductions** — Adana Demirspor withdrew
   during 2024-25 (336 played matches instead of 342) and carried
   `adjust_points_ADE=-12`. Awarded forfeit results appear in the standings but
   not the matrix.

Consequently the diff is a **reported warning, not a hard assertion**: forfeits
correctly do not train a goals model, so a mismatch on a withdrawal season is
expected and desirable. The check exists to catch parser regressions, and any
season whose diff exceeds a small tolerance without a known withdrawal fails
the build.

### Output and wiring

The converter writes `data/superlig_results.csv` in the **existing** history
schema (`date, home_team, away_team, home_score, away_score, tournament, city,
country, neutral`) so `history.rs` parses it unchanged. `neutral` is always
false. Matches carry a per-season nominal date; with a 1460-day half-life,
intra-season date precision is immaterial to the fit.

`TeamIndex::wc()` → `TeamIndex::league()`, built from the same `data::elo()`
order so DC and pi indices continue to coincide with `World` indices.
`ROW_TEAM_NAME` becomes `"Other Club"`.

**What the bucket actually is.** By construction it absorbs every match of
every club not in the current 18 — Sivasspor's mid-table years, Hatayspor,
Adana Demirspor's collapse season, all of it. It is a *league-average departed
club*, not a newly-promoted baseline, and the spec names it accordingly rather
than implying a precision it does not have.

**Consequence for promoted clubs, accepted and stated.** Amedspor and Çorum
have no top-flight history, so for them the ensemble components systematically
disagree: ClubElo supplies a club-specific rating (Amedspor 1663) while DC and
pi can only return bucket-average strength. The Elo component is therefore the
only club-specific signal for promoted clubs, and with default weights
(`0.5,0.3,0.2`) their projections are pulled toward league-average. This is an
accepted property of the design, not a defect to paper over. Erzurumspor is
the intermediate case: real but heavily time-decayed history from five seasons
ago.

`data/dc_params.json` is refit via `cargo run --release --example fit_dc`
against the new index; the server loads it via `include_str!` as before.

**Explicitly out of scope:** TFF 1. Lig results. Including them would let DC
estimate promoted clubs directly, but against a systematically weaker opponent
pool with no cross-tier calibration, which would overrate them.

## 8. Calibration

ClubElo's scale is compressed relative to international Elo — 1509–1779 here
versus 1435–2055 before — so `BASE`, `D_DIV`, and `HOME_ADV` are **verified,
not inherited**. Acceptance: simulated mean goals per side, and simulated home
win / draw / away win rates, must match the empirical rates in
`data/superlig_results.csv` within a stated tolerance. Constants are tuned
until they do. Without this step the Elo component silently mis-scales.

**Re-verify the ratings before hardcoding them.** The 18 ClubElo values in §2
came through a single fetch summarized by a small model. A transcription error
becomes a miscalibrated prior baked into `data.rs` that no test would catch, so
implementation re-fetches the table and spot-checks the values before they are
committed.

## 9. Scraper (`src/scraper.rs`)

- Drop `ELO_RATINGS_URL` and `ELO_TEAMS_URL` (international ratings).
- **Retarget the live scrape to TFF** (`pageID=198`), not Wikipedia. TFF is
  authoritative, updates immediately, carries round numbers, and is the same
  page the fixture list comes from — so one fetch refreshes both the calendar
  and the results. Wikipedia was demonstrably stale for matchday 1.
- Decode as **windows-1254**.
- Unplayed fixtures render their score cell as `-`. The parser must skip them
  rather than coerce a zero, and a test must cover it — this is the case the
  historical seasons never exercise and the live page always will.
- `update_from_live` overlays results onto `world.played` by `(home, away)`.
- Retain the existing behavior of dropping unrecognized names without
  panicking, with its test.

Two parsers therefore exist, with different jobs and separate tests: the
**wikitext** parser (§7) builds the historical training set from completed
seasons, and the **TFF HTML** parser handles the live 2026-27 season. Both
normalize into the same canonical club names.
- `update_from_live` mutates `world.played` only; it remains the sole path that
  changes shared state.
- Retain the existing behavior of dropping unrecognized names without
  panicking, with its test.

## 10. LLM scenarios (`src/llm.rs`)

Same model, same strict-JSON contract, same `strip_fences`, same server-side
`validate_elo_overrides`. Changes: the system prompt enumerates the 18 club
names and uses club-football heuristics (injury, suspension, transfer in/out,
manager change, European fixture congestion) instead of international ones, and
validation bounds are rescaled to ClubElo's range. LLM output stays untrusted.

## 11. Testing

Ported and kept:

- `simulate_is_deterministic_for_same_seed` — hard invariant
- `simulate_counts_sum_to_n_sims`
- `elo_override_changes_ratings`
- `ensemble_builds_from_embedded_data_and_blends_lambdas`
- `elo_only_weights_reproduce_pure_elo_lambdas`
- `update_from_live_drops_unrecognized_names_without_panicking`
- `lam_pair` symmetry, now asserting the home boost applies to the fixture's
  home side rather than a host flag

New:

- Fixture completeness: 306 fixtures, every club plays 34, every pair meets
  exactly twice with opposite home/away
- `rank_table` head-to-head ordering against a hand-built tie where H2H and
  overall GD disagree — the case that proves the Süper Lig rule is implemented
  rather than the World Cup one
- Recorded results are respected and never resampled
- Position counts sum to `n_sims` for every club
- Relegation counts equal the count of finishes in positions 16-18
- History parser: a fixture-file season round-trips to its standings

## 12. Out of scope for v1

Turkish Cup, a modelled play-off tiebreak beyond a coin flip, in-season points
deductions, and player-level modelling.

(The official TFF calendar was listed here in the first draft as out of scope.
It is now in scope — see §2 — because the full 306-fixture season proved to be
available after all.)

## 13. Housekeeping

The Cargo package is renamed; the repository directory name stays `wc2026-sim`
so the existing Railway deployment link keeps working.

**The Dockerfile changes in the same commit as the rename.** Renaming the
package renames the built binary, and the Dockerfile both copies
`target/release/<name>` and keys its dependency-caching dummy-`main.rs` layer
to the package name. Missing this breaks the Railway deploy rather than the
local build, so it will not surface in `cargo test`.

Work happens on `agent/superlig-2026-27`, branched fresh off `main`. Both
`README.md` and `README.tr.md` are rewritten — the Turkish README becomes the
more natural primary for this subject. `CLAUDE.md` is updated in the same
change, since nearly every architecture note in it describes the tournament
model being deleted.
